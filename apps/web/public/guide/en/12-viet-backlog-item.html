Rova User Guide / 12. Agile Guideline
PART 12 · AGILE GUIDELINE

Write clearly enough for mutual understanding, evaluation, and testing

A well-described backlog item problem or value to be achieved, the conditions must be true and the scope boundary. This section guides two frequently used types on Rova: User Story and Defect.

After this chapter, you will be able to
  • Write a User Story with clear personas, goals, and values.
  • Write Acceptance Criteria using Given–When–Then.
  • Defect record is reproducible and verifiable.
  • Distinguish Defect from change request.
  • Self-check items before refining.
12.1

Write User Story

User Story describes a small value that a user or stakeholder needs to receive.

Use User Stories when the work creates a behavior or result that can be delivered and tested independently. The title should start with a verb and clearly state the result, for example “Filter Backlog by Priority”. Avoid generic titles like “Improve Backlog” or “Make a filter screen”.

Template User Story

Title[Verb + object + desired result]

As a[specific persona or role]

I want to[action or outcome to be performed]

So that[value received or problem resolved]

Business Rules[permissions, scope and limits confirmed]

Acceptance CriteriaGiven [context] · When [action] · Then [observable result]

Non-scope[content easily misunderstood but not part of Story]

Open questions[missing information needs PO/BA confirmation]

IngredientsHow to writeShould be avoided
PersonaSelect the person who directly receives the value or is responsible for the result.Use “user” in all cases without defining roles.
GoalDescribes an action or outcome, small enough to be completed in an Iteration.List screens, APIs or code instead of needs.
ValueArticulate improved decision, time, or risk.Repeat verbatim part I want to.
Business RulesRecord permissions, scope, status and conditions that have been confirmed by the source.Manually adding a rule, SLA or notification has not been agreed upon.
Acceptance CriteriaEach AC describes a situation and observable outcome.Write as a detailed Test Case or describe how to deploy.

Acceptance Criteria does not replace Test Case. AC determines the acceptance conditions of Story; QA can develop additional test data, variations, and technical inspections.

The example below is used to illustrate how to fill out the template. Business Rules and AC must be confirmed by PO/BA before creating the actual Story.

Illustrative example: Filter Backlog by Priority

As aEditor of Team Maintainer

I want tofilters Backlog according to one or more Priorities

So thatI can focus on handling important Work Items within the assigned scope

Rule 1Results only include Work Items belonging to Projects and Teams that users are allowed to view.

Rule 2Clearing all Priority options will return the list to an unfiltered state by Priority.

AC 1Given Backlog has Work Items in many Priorities, When the user selects High, Then list only shows Work Items with Priority High in the current scope.

AC 2Given High filter is applied, When the user deselects High, Then Backlog displays all Priorities in the current scope again.

Non-scopeSave filters as personal views and share filters.

Check according to INVEST before refining:

I
Independent

Can be deployed and accepted without strong dependence on many unknown Stories.

N
Negotiable

State the needs and boundaries, still allowing the Team to exchange solutions.

V
Valuable

Persona gains explicit value when Story is completed.

E
Estimable

Team understands enough scope, rules and dependencies to estimate.

S
Small

Small enough to complete in one Iteration; otherwise, split by stream or rule.

T
Testable

AC has observable results and is not dependent on subjective feelings.

12.2

Write Defect

Defect records the difference between the actual behavior and the expected result.

Only create a Defect when there is evidence that the system is different from the requirement, Acceptance Criteria or approved behavior. If a user wants a capability that was never requested, it's usually a User Story or change request.

Template Defect

Title[Function] – [wrong behavior] when [condition]

ContextProject, Team, monitor, version or environment error occurred

PreconditionData, permissions and status required before rendering

StepsActions are short, in the correct order, and do not combine multiple actions

ActualActual results observed

ExpectedThe result is correct according to the rule or AC has been confirmed

SeverityTechnical or business impact level

PriorityThe order to be processed depends on the product decision

EvidencePhotos, videos, logs, timestamps and related data IDs

LinksRelated User Story, Feature or Defect

FieldMinimum standardsFailed example
TitleTells the main functions, misbehaviors and conditions.“Filter error”, “Not running”, “Bug Backlog”.
StepsOthers can iterate on the same data and permissions.“Go to Backlog and try filtering”.
ActualCorrect description of what is seen, including value or message if any.“Incorrect result”.
ExpectedBind to confirmed rule or AC.Propose a new feature that is not in the requirements.
EvidenceShows the time, scope, and enough data for traceability.The image omits the related URL, Project, Team, or status.

Defect below illustrates how to record. Only create real items after recreating and having a source confirm Expected.

Illustrative example: Backlog – High filter still displays Medium item

ContextRova web · Project ROVA · Team Maintainer · Backlog page

PreconditionAccount has permission to view Team; Backlog has at least one High item and one Medium item.

Step 1Open Backlog and confirm correct Project and Team.

Step 2Open Filters and select Priority = High.

ActualThe list still shows Work Item with Priority Medium.

ExpectedThe list only displays Work Items that have Priority High in the current scope.

EvidenceFull screen image with context selector, High filter and Medium line; with time and Work Item ID.

LinksUser Story “Filter Backlog by Priority”, AC 1.

Severity and Priority are not the same. Severity describes the impact level; Priority is the decision to process sooner or later. A minor interface bug can still have high Priority if it is on an important demo stream.

01
Unable to reproduce

Add permissions, Project, Team, sample data, browser, when and how often.

02
Expected has no source yet

Link requirement or AC. If there is no agreement on the correct behavior, ask the PO/BA before concluding that it is Defective.

03
A Defect contains many errors

Separate by cause or effect that can be edited and independently verified.

05
Photos only

Photos are proof, do not replace Steps, Actual and Expected.

Check yourself before putting items into refinement
  • Does the User Story clearly state persona, goal and value?
  • Does each Acceptance Criteria have an observable result?
  • Does Defect have enough Context, Steps, Actual and Expected?
  • Expected already has a source, or is this essentially a new request?
